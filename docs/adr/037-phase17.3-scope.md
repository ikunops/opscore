## 0. Abstract

**Phase 17 is CLOSED** (ADR-035 Scope → ADR-036 Architecture → implementation → R79 Defect Repair, all
signed PASS). The management write surface (`/management/v1`, bind `:8082`) now implements the
**INTENT → CAS → OUTCOME** three-phase audit protocol (MUST-P17-9/13), is fail-closed (MUST-P17-14), and
is physically isolated from the frozen read contract (ADR-036 §3.6).

R79 (A — PASS) confirmed the write path is correct, but surfaced a class of **audit-trustworthiness gaps**
that the write protocol alone does not close. These are not bugs in the mutation logic; they are missing
**reconciliation** guarantees around the audit trail the write surface produces:

1. **Orphaned-INTENT hazard (crash/recovery).** Between `commit()` (CAS succeeds, repository mutated)
   and the OUTCOME record being appended, a process crash / DB blip leaves an `intent` record with **no
   matching `outcome`** for the same `correlationID`. The repository IS changed but the audit shows only
   an unresolved intent. Nothing today detects this.
2. **Management owns an audit it cannot read.** The write surface *appends* to the audit store but
   exposes **no read endpoint** for the audit it owns. Operators can only see `external/v1` governance
   *summaries* (read-only Public Contract) — never "what did management actually do." There is no
   management-scoped audit viewer.
3. **`correlationID` is recorded but never used.** It exists to support replay/idempotency reasoning, but
   no guard rejects (or even flags) a new mutation whose `correlationID` collides with an existing
   terminal `outcome` (true replay protection is absent).
4. **No post-hoc revision authority.** The OUTCOME carries the actually-committed `revision`, but nothing
   scans for INTENT→OUTCOME revision consistency, so a silently-dropped outcome (gap #1) is invisible.

**Phase 17.3 thesis:** make the management write-audit *self-verifiable and operator-visible* — add a
read-only **reconciliation scanner**, a management-scoped **audit read surface**, and a `correlationID`
**replay guard** — **without** touching `external/v1`, **without** a Control Plane, and **without**
altering the INTENT→CAS→OUTCOME protocol semantics (reconciliation is additive on top).

## 1. Phase 17.3 positioning — hardening the audit, not the write path

| Layer | Phase 17.0/1/2 (CLOSED) | Phase 17.3 (this ADR) |
|---|---|---|
| Write path | INTENT → CAS → OUTCOME, fail-closed, isolated | **unchanged** |
| Audit store | `Append` only, `correlationID`/`revision`/`result` columns (v4) present | **read** added; schema unchanged |
| Read exposure | `external/v1` governance *summary* (frozen) | **new** management-scoped audit *viewer* (read-only, on `:8082`) |
| Reconciliation | none | **scanner** (orphaned-intent detection + best-effort forward clamp) |
| Replay protection | none | `correlationID` guard (reject/flag on collision) |

Phase 17.3 is the deliberate **audit-trustworthiness counterpart** to Phase 17.2: 17.2 made the write
path correct-and-audited; 17.3 makes the audit *provably complete and operator-visible*.

> **Phase 17.3 Boundary (R17-0):** The frozen `external/v1` read-only Public Contract is **UNCHANGED**.
> The new audit read surface lives **only** on the `:8082` management bind under `/management/v1/audit`
> (or equivalent management namespace), never under `external/v1`. This is the same surface-separation
> invariant as P17-0/P17-1, inherited and extended.

## 2. Freeze boundaries (inherited + new)

- **MUST-R17-1 — `external/v1` read-only Public Contract unchanged.** No new read or write path added to
  it; the audit viewer is a management-surface concern (R17-0).
- **MUST-R17-2 — No Control Plane / orchestration / new process.** Reconciliation is an **in-process,
  on-demand (or startup best-effort) scan** — there is **no** scheduler daemon, no leader election, no
  multi-node coordination. A separate long-running reconciler process is explicitly out of scope.
- **MUST-R17-3 — The INTENT→CAS→OUTCOME protocol is NOT modified.** Reconciliation is **additive** on
  top of the existing three-phase semantics. The mutation pipeline (AuthN → AuthZ → Validation → Handler
  → CAS → Audit) keeps its correctness and ordering; 17.3 only *reads* the resulting audit and *guards*
  replay at the entry.
- **MUST-R17-4 — Fail-safe, forward-only reconciliation.** An orphaned `intent` whose underlying
  mutation **can be proven committed** (repository revision advanced) is reconciled **forward** by
  synthesizing a `success` outcome. An orphaned `intent` that **cannot** be proven committed is
  **reported**, never silently dropped. A **committed** mutation is **NEVER auto-rolled-back** by
  reconciliation (fail-safe).
- **MUST-R17-5 — `AuditStore` interface change is ADDITIVE only.** A new method
  `ListByCorrelation(correlationID string, limit int) ([]AuditEvent, error)` is added; the existing
  `Append` / `List` / `ListByOperation` signatures are untouched (no breaking change, no v4→v5 migration).
- **MUST-R17-6 — Frozen packages unmodified.** `internal/platform`, `internal/governance`,
  `internal/plugin/{runtime,isolation}`, `internal/controlplane/hostregistry`, `internal/external`,
  `internal/governancepolicy` (Repository/CAS layer), `internal/platformview` are NOT modified. The audit
  schema already carries `correlationID` / `revision` / `result` (v4, ADR-035/036); reconciliation derives
  entirely from those existing fields — **no schema migration**.
- **MUST-R17-7 — Management audit read surface is read-only.** It adds `GET` endpoints only on `:8082`;
  no new mutation endpoint is introduced beyond the Phase 17.2 set.
- **MUST-R17-8 — AuthN/AuthZ applies to the new read surface too.** The audit viewer is gated by the
  same token authenticator (MUST-P17-14); unauthenticated reads are rejected fail-closed.
- **MUST-R17-9 — No new dependency.** Reuse the existing `AuditStore`, `encoding/json`, and the
  `governancepolicy.Repository` read of current revision (the Repository's existing `Get`/`CurrentRevision`
  accessor, consumed as-is). No new Go module / runtime library.

## 3. Phase 17.3 scope — Management Audit / Reconciliation Hardening

**Goal.** Make the management write-audit *complete, self-verifiable, and operator-visible*:
- detect orphaned INTENT records (audit completeness),
- expose the audit the management surface owns (operator visibility),
- reject replayed mutations via `correlationID` (replay protection),
all without extending `external/v1` or introducing a Control Plane.

### 3.1 Candidate scope items (proposed)

1. **Reconciliation scanner (read-only pass over `AuditStore`).** Detects `intent` records that have **no
   matching terminal `outcome`** (`success`/`failure`) for the same `correlationID` within a policy. Uses
   the additive `ListByCorrelation` (MUST-R17-5). Pure read; never mutates the repository.
2. **Best-effort forward reconciliation (fail-safe).** For each orphaned `intent`, consult the
   `governancepolicy.Repository` current revision for that `policyID`:
   - if the committed `revision` (from the orphaned intent's expected revision + 1, or the repository's
     current revision) proves the mutation landed → synthesize a `success` outcome record
     (reconcile **forward**), MUST-R17-4.
   - if it cannot be proven → emit a **reconciliation-report entry** flagged `unresolved` (reported, not
     dropped).
   **Never** rolls back a committed mutation.
3. **Management-scoped audit read surface (read-only, on `:8082`).**
   - `GET /management/v1/audit?policy={id}&result={intent|success|failure}&limit=N` — list management
     audit events it owns (NOT external/v1 governance summaries).
   - `GET /management/v1/reconciliation` — run the scanner (or return the last cached report) and return a
     stable, parseable JSON reconciliation report (orphaned intents, resolutions, unresolved items).
   Both gated by the existing token authenticator (MUST-R17-8).
4. **`correlationID` replay guard (entry-point).** On a new mutation, before the INTENT phase, check
   whether the supplied `correlationID` already has a terminal `outcome`. If so, **reject** the mutation
   (configurable: strict-reject `409` vs. flag-and-allow) — true replay protection, no silent
   double-apply.
5. **Additive `AuditStore.ListByCorrelation`** (MUST-R17-5) — the only storage-interface change; supports
   the scanner and the replay guard efficiently without full-table scans.

### 3.2 MUST (Phase 17.3 iron laws)

- **R17-0 — `external/v1` read-only Public Contract UNCHANGED; audit viewer is management-surface only.**
- **R17-1 — No Control Plane / orchestration / new process** (MUST-R17-2); reconciliation is in-process.
- **R17-2 — INTENT→CAS→OUTCOME protocol unchanged** (MUST-R17-3); reconciliation is additive.
- **R17-3 — Fail-safe, forward-only reconciliation** (MUST-R17-4); committed mutations never auto-rolled-back.
- **R17-4 — `AuditStore` change additive only** (MUST-R17-5); no breaking signature, no schema migration.
- **R17-5 — Frozen packages unmodified** (MUST-R17-6); derive from existing `correlationID`/`revision`/`result`.
- **R17-6 — Audit read surface is read-only** (MUST-R17-7); no new mutation endpoint.
- **R17-7 — AuthN/AuthZ on the read surface** (MUST-R17-8); fail-closed.
- **R17-8 — No new dependency** (MUST-R17-9).

### 3.3 SHOULD (Phase 17.3)

- **R17-S1** Reconciliation report is stable/parseable JSON (machine-readable; suitable for alerting).
- **R17-S2** `correlationID` replay guard is deployment-configurable (strict-reject vs. flag-and-allow,
  collision window).
- **R17-S3** Scanner runs best-effort at server startup (non-blocking) and on-demand via
  `GET /management/v1/reconciliation`.

### 3.4 Out of scope (Phase 17.3)

- Modifying `external/v1` (frozen read contract) — explicitly forbidden (R17-0).
- Control Plane / HA / orchestration / scheduler daemon / leader election (R17-1).
- Any change to the INTENT→CAS→OUTCOME mutation semantics (R17-2).
- Auto-rollback of committed mutations (explicitly forbidden — fail-safe forward only, R17-3).
- New storage engine, new dependency, or audit-schema migration (R17-4/R17-8).
- Any change to the read-only probe (`/healthz` `/readyz` `/versionz`) or the Runtime Contract.
- New capability ownership in Phase 8 packages; new Plugin Ecosystem contract.

## 8. R80 additional guidance — MUST-17.3-A carry-forward to ADR-038

Per the R80 verdict, the `correlationID` replay guard MUST be **strict-reject (409)** — there is **NO**
configurable allow mode in Phase 17.3:

> **MUST-17.3-A** — If a terminal `outcome` already exists for the supplied `correlationID`, the mutation
> request is **rejected with `409 Conflict`**. The scope's earlier "configurable strict-reject vs.
> flag-and-allow" (R17-S2) is **withdrawn** for Phase 17.3; replay policy flexibility, if ever needed,
> is a separate Major/ADR, not a Phase 17.3 toggle. Rationale: `correlationID` is the mutation identity
> boundary; permitting a new mutation under an already-terminal `correlationID` would fork a single
> causal chain into many, degrading audit causal integrity — the opposite of reconciliation's goal.

ADR-038 MUST also resolve (R80 guidance): (1) Scanner ↔ Management Handler boundary; (2) `AuditStore`
read model (incl. `ListByCorrelation` is a *query view only*, not the replay-protection consistency
proof); (3) `ReconciliationReport` schema (`correlationID`, `policyID`, `intentRevision`,
`observedRevision`, `status`, `resolution`); (4) replay-guard race handling; (5) startup best-effort
scan is allowed, in-process, non-blocking; (6) **no background controller / scheduler / worker**.

## 7. R80 additional guidance — required answers for ADR-038 (Phase 17.3 Architecture)

Per the ADR-021 three-tier discipline, the Phase 17.3 Architecture ADR (ADR-038) MUST resolve, carrying
the boundaries above into concrete decisions:

### 7.1 Reconciliation scanner (carries R17-2/R17-3/R17-4)
- **Detection algorithm** — how is an orphaned `intent` identified from `ListByCorrelation` results?
  (intent present, no `success`/`failure` sharing `correlationID`; within a policy; within a bounded age.)
- **Forward reconciliation** — how is "mutation provably committed" established against
  `governancepolicy.Repository` current revision, and how is the synthesized `success` outcome written
  (re-using the existing `Append`, with a `reconciled:true` marker in `detail`)?
- **Unresolved handling** — what does the report contain for an item that cannot be proven committed, and
  where is it surfaced (persisted report file? in-memory cache? returned by `GET /reconciliation`)?

### 7.2 Audit read surface (carries R17-0/R17-6/R17-7)
- **Endpoints** — exact routes on `:8082` (e.g. `GET /management/v1/audit`, `GET /management/v1/reconciliation`),
  query params, response shape.
- **Mechanical isolation** — how is it *proven* these routes are served only by the management mux
  (reuse the ADR-036 §3.6 `assertNoManagementRoutes` build assertion, extended to the new routes)?
- **AuthN/AuthZ** — reuse the existing token authenticator; how is the read gate wired so an
  unauthenticated `GET` is rejected fail-closed (R17-7)?

### 7.3 `correlationID` replay guard (carries R17-2/R17-9)
- **Entry-point check** — where in the mutation pipeline (before the INTENT phase) is the collision check
  placed, using `ListByCorrelation`?
- **Policy** — strict-reject (`409`) vs. flag-and-allow; collision-window config; how the decision is
  recorded in the audit (`detail` marker).

### 7.4 `AuditStore.ListByCorrelation` (carries R17-4/R17-5)
- **Signature & SQL** — exact method signature, the `WHERE correlation_id = ? ORDER BY ... LIMIT ?` query,
  and the SQLite migration posture (none — existing column; additive index optional).
- **Backfill** — does the in-memory / sqlite implementation need any index addition (non-breaking `CREATE INDEX IF NOT EXISTS`)?

### 7.5 Mechanical isolation guarantees (carries R17-0/R17-5/R17-6)
- **No execution bridge** — reconciliation reads `governancepolicy.Repository` (read of current revision)
  only; it MUST NOT call `Save`/`Activate`/`Deactivate`/`Archive` (extend the existing `TestNoCASBypass`
  AST guard, or add `TestReconciliationDoesNotMutate`, to prove the scanner is read-only).
- **Frozen-package zero-diff** — `git diff` of frozen packages MUST be empty; the only storage change is
  the additive `ListByCorrelation` + optional non-breaking index.

### 7.6 ADR-038 acceptance gate
ADR-038 is signed only when **all** of 7.1–7.5 have a concrete, reviewable answer and the mechanical
guards (7.5) are specified. No scanner/handler is implemented until then.

# 00-设计原则

> OpsCore Architecture Principles v1.0
> **本文档是整个项目的"宪法"。** 后续所有设计文档（01-13）必须遵守本文档定义的定位、边界、抽象和约束。
> 任何与本文档冲突的设计，以本文档为准。

---

## 1. 系统定位

### 1.1 一句话定义

> **OpsCore 是一个 Operations Control Plane（运维控制平面）。**

### 1.2 OpsCore 是什么

OpsCore 负责：

| 职责 | 说明 |
|------|------|
| **统一身份** | 所有用户、服务账号、Session 由 Control Plane 管理和验证 |
| **统一权限** | 所有操作的授权决策由 Permission Engine 统一完成 |
| **统一执行** | 所有系统操作的执行由 Executor 统一调度，禁止绕过 |
| **统一审计** | 所有操作的审计记录由 Audit Writer 统一写入 |
| **统一插件治理** | 插件的注册、权限、能力、生命周期由 Control Plane 统一管理 |

### 1.3 OpsCore 不是什么

```
❌ OpsCore 不是 Docker 管理工具
❌ OpsCore 不是 Kubernetes 管理工具
❌ OpsCore 不是数据库管理工具
❌ OpsCore 不是监控告警系统
```

真正干活的是：

```
OpsCore Control Plane
├── Core Built-in Module（内置模块：系统服务、网络防火墙等）
└── Plugin（插件：Docker、Kubernetes、MySQL 等）
```

Control Plane 不直接操作业务资源，它只负责**调度、授权、审计**。具体的操作由 Built-in Module 和 Plugin 通过 Executor 执行。

### 1.4 定位约束

- Control Plane 的代码**不包含任何特定业务逻辑**（如 Docker API 调用、K8s CRUD）
- 新增任何业务能力，必须以 **Built-in Module** 或 **Plugin** 的形式接入，不能直接写进 Core
- 后续增加 Docker、Kubernetes、MySQL、Redis、CI/CD 等，都是插件扩展，不修改 Core 架构

### 2.2 依赖规则（铁律）

**所有模块只能向下依赖，不能反向依赖。**

```
Client      → API Gateway → Control Plane → Dispatcher → Module/Plugin → Executor → OS
                                                                    ↑
                                                    插件不能直接操作 OS
                                                    必须经 Executor 执行
```

具体约束：

| 模块 | 可以依赖 | 不可依赖 |
|------|----------|----------|
| API Gateway | Auth | Executor、Module、Plugin |
| Permission Engine | DDL（permissions 表） | Executor |
| Capability Engine | DDL（host_capabilities 表） | Executor |
| Policy Engine | DDL（policies 表） | Executor |
| Dispatcher | Permission/Capability/Policy Engine | Executor 实现 |
| Built-in Module | Executor、Context | Plugin Gateway |
| Plugin Gateway | Plugin Process（RPC） | Built-in Module |
| Plugin Process | Executor（通过 RPC 回调）、Context | Core 内部模块 |
| Executor | Sandbox、OS | Module 逻辑、Plugin 逻辑 |
| Audit Writer | DDL（audit_logs 表） | 任何业务逻辑 |

## 3. 设计哲学

### P1. Control Plane 与 Executor 分离

Control Plane（认证、权限、策略、调度）不执行任何系统命令。
Executor 只执行已经过 Control Plane 全部校验的命令。

```
决策权 → Control Plane
执行权 → Executor
两者分离，互不越界
```

### P2. Everything is Command

系统内部所有操作统一抽象为 **Command**，不绑定传输协议。

```
REST API  →  Command  →  Dispatcher  →  Module/Plugin  →  Executor
CLI       →  Command  →  Dispatcher  →  Module/Plugin  →  Executor
SDK       →  Command  →  Dispatcher  →  Module/Plugin  →  Executor
WebSocket →  Command  →  Dispatcher  →  Module/Plugin  →  Executor
```

REST 只是 Command 的一种传输层，不是系统内核。CLI、SDK、WebSocket 未来都复用同一套 Command 调度。

Command 结构：

```json
{
    "command": "system.service.restart",
    "resource": "service/nginx",
    "params": { "timeout": 30 },
    "meta": { "dry_run": false, "async": false }
}
```

### P3. 插件不能直接执行 Shell

```
❌ Plugin → os.Exec("systemctl restart nginx")
✅ Plugin → ctx.Executor.Execute("system.service.restart", params)
```

插件必须通过 Executor 执行系统操作。这保证了：
- 所有执行都经过权限校验
- 所有执行都有审计记录
- 所有执行都有超时和沙箱保护

### P4. Capability 统一抽象

插件不自己探测系统能力，只查询 Capability Engine：

```
❌ Plugin → os.Stat("/var/run/docker.sock")
✅ Plugin → ctx.Capability("docker.sock")
```

Capability Engine 负责探测、缓存、更新所有主机能力。插件只消费，不探测。

### P5. 统一 Context 传递

所有接口、所有模块、所有插件，统一接收 `Context`：

```go
// ❌ 错误：分散传参
func Execute(user User, host Host, perm []string, logger Logger)

// ✅ 正确：统一 Context
func Execute(ctx Context)
```

Context 自动携带：User、Host、Permission、Capability、TraceID、RequestID、Logger、Config。审计、日志、Trace、权限全部自动继承。

### P6. 审计不可绕过

没有不经审计的执行。审计是 Executor 的后置中间件，不是可选步骤。

### P7. 向下兼容，不向前兼容

- 新版本可以新增字段、新增表、新增 API
- 新版本不能删除已有字段、改变已有语义
- DDL 变更必须通过 migration，不允许直接 ALTER

## 4. 核心抽象

### 4.1 Context（统一上下文）

```go
type Context struct {
    // 身份
    User       UserContext       // 当前用户
    Host       HostContext       // 目标主机

    // 权限与能力
    Permission PermissionContext // 用户权限快照
    Capability CapabilityContext // 主机能力快照

    // 链路追踪
    TraceID    uuid.UUID         // 审计链路 ID
    RequestID  string            // HTTP 请求 ID

    // 基础设施
    Logger     Logger            // 结构化日志（自动带 TraceID）
    Config     ConfigProvider    // 配置读取（从 config_items 表）
    Executor   ExecutorInterface // 执行器引用（插件通过此执行命令）
}
```

**规则**：
- Context 在请求入口创建，贯穿整个调用链
- Context 是只读的（除 Executor 引用外）
- Context 不可为 nil，无用户场景（如登录）使用 SystemContext
- 所有日志自动注入 TraceID，不需要手动传

### 4.2 Resource（可操作对象）

Resource 不是数据库记录，是**系统中可被操作的对象**。

```
Resource 类型：
├── Server          (物理机/虚拟机)
├── Service         (systemd 服务)
├── Container       (Docker 容器)
├── Namespace       (K8s 命名空间)
├── Deployment      (K8s 部署)
├── FirewallRule    (防火墙规则)
├── Port            (网络端口)
├── File            (配置文件)
├── Database        (数据库实例)
├── Table           (数据库表)
├── Backup          (备份)
└── ... (插件可扩展)
```

Resource 表示为路径：

```
service/nginx           → 类型=service, 名称=nginx
container/redis         → 类型=container, 名称=redis
firewall/rule/80-tcp   → 类型=firewall_rule, 名称=80-tcp
```

权限 = Resource Type + Action：

```
resource_type=service     action=restart     → system.service.restart
resource_type=firewall    action=create      → network.firewall.rule.create
resource_type=container   action=restart     → docker.container.restart
```

### 4.3 Capability（系统能力）

Capability Engine 统一管理所有主机能力，插件只查询不探测：

```
Capability 类型：
├── root                 (root 权限)
├── systemd              (systemd 可用)
├── journal              (journalctl 可用)
├── docker.sock          (Docker Socket 可访问)
├── k8s.kubeconfig       (K8s kubeconfig 可用)
├── nftables             (nftables 可用)
├── iptables             (iptables 可用)
├── cgroup.v2            (cgroup v2 可用)
├── selinux              (SELinux 启用)
├── apparmor             (AppArmor 启用)
├── systemd.resolved     (systemd-resolved 可用)
├── firewalld            (firewalld 可用)
└── ... (插件可注册新 Capability Probe)
```

### 4.4 Command（操作命令）

Command 是系统内核的统一操作单元：

```go
type Command struct {
    Name     string            // "system.service.restart"
    Resource string            // "service/nginx"
    Params   map[string]any    // {"timeout": 30}
    Meta     CommandMeta       // dry_run, async, timeout
}

type CommandMeta struct {
    DryRun  bool
    Async   bool
    Timeout time.Duration
}
```

REST 到 Command 的映射示例：

```
POST /api/v1/system/services/nginx/restart
  → Command{Name: "system.service.restart", Resource: "service/nginx"}

POST /api/v1/network/firewall/rules
  → Command{Name: "network.firewall.rule.create", Resource: "firewall", Params: {port: 80, protocol: "tcp"}}

POST /api/v1/plugins/docker/containers/redis/restart
  → Command{Name: "docker.container.restart", Resource: "container/redis"}
```

### 4.5 Permission（权限）

权限不再是字符串解析，而是结构化关联：

```
Permission = ResourceType × Action

permissions 表：
  id | resource_type_id | action_type_id | code
  ---|------------------|----------------|-----
  1  | service          | restart        | system.service.restart
  2  | service          | stop           | system.service.stop
  3  | firewall_rule    | create         | network.firewall.rule.create

resource_types 表：
  id | name        | domain
  ---|-------------|--------
  1  | service     | system
  2  | firewall    | network
  3  | container   | docker (plugin)

action_types 表：
  id | name
  ---|--------
  1  | read
  2  | create
  3  | update
  4  | delete
  5  | restart
  6  | stop
  7  | start
```

好处：
- 不用字符串解析 `system.service.restart` 拆分
- 数据库 JOIN 查询效率更高
- 新增 Resource Type / Action Type 是数据操作，不改代码
- 插件注册新资源类型 = INSERT resource_types

### 4.6 Plugin（插件）

Plugin 是 Control Plane 的扩展单元，通过 Manifest 声明一切：

```yaml
# plugin.yaml (Plugin Manifest)
name: docker
version: "1.0.0"
description: "Docker 容器管理插件"
schema_version: "1.0"

# 依赖的系统能力
capabilities:
  - docker.sock

# 注册的资源类型
resources:
  - type: container
    domain: docker
    actions: [read, start, stop, restart, delete]

# 注册的权限
permissions:
  - resource_type: container
    action: read
    description: "查看容器"
  - resource_type: container
    action: restart
    description: "重启容器"

# 注册的操作（Command）
operations:
  - name: docker.container.restart
    resource_type: container
    action: restart
    executor: plugin          # 由插件自己处理
    risk_level: medium
    timeout: 60s
    params:
      container_name:
        type: string
        required: true
        pattern: "^[a-zA-Z0-9_-]+$"

# 插件配置项
config:
  - key: socket
    default: "/var/run/docker.sock"
    type: string

# 数据库迁移
migrations:
  - version: "1.0.0"
    file: "migrations/0001_docker.sql"

# 前端菜单
menus:
  - name: "Docker"
    path: "/docker"
    permission: "docker.container.read"
    icon: "docker"

# API 路由（转发到 Plugin Gateway）
routes:
  - method: GET
    path: "/containers"
    command: "docker.container.list"
    permission: "docker.container.read"
  - method: POST
    path: "/containers/{name}/restart"
    command: "docker.container.restart"
    permission: "docker.container.restart"
```

插件安装时，Core 根据 Manifest 自动：
1. 写入 `plugins` 表
2. 注册 `resource_types` + `permissions`
3. 注册 Operations 到 Registry
4. 执行 migrations
5. 写入 `plugin_configs`（默认配置）
6. 注册前端菜单
7. 注册 API 路由
8. 探测 capabilities

**零代码接入**——插件开发者只需写 Manifest + Plugin 代码，不需要手动注册任何东西。

## 5. Executor 分层

Executor 不是单一组件，按操作域分层：

```
Executor (统一入口)
├── System Executor      → systemctl, hostname, timedatectl
├── Network Executor     → iptables, nftables, ip, ss
├── File Executor        → 文件读写/备份/恢复
├── Process Executor     → 进程查询/终止
└── Plugin Executor      → 转发给 Plugin Process（RPC）
```

### 5.1 分层规则

| 操作类型 | Executor | 示例命令 |
|----------|----------|----------|
| 服务管理 | System Executor | `systemctl restart nginx` |
| 防火墙 | Network Executor | `iptables -A INPUT -p tcp --dport 80 -j ACCEPT` |
| 配置文件 | File Executor | 读写 /etc/nginx/nginx.conf |
| 进程管理 | Process Executor | `kill -TERM 1234` |
| Docker | Plugin Executor | 转发给 docker 插件进程 |
| K8s | Plugin Executor | 转发给 kubernetes 插件进程 |

### 5.2 插件执行路径

```
Plugin 收到 Command
    │
    ├─ 需要执行系统命令？
    │     │
    │     ▼
    │  ctx.Executor.Execute("system.xxx", params)
    │     │
    │     ▼
    │  System/Network/File Executor → OS
    │
    └─ 自己处理（如调用 Docker API）？
          │
          ▼
       Plugin 内部逻辑
          │
          ▼
       返回结果（仍经审计）
```

插件有两种执行模式：
1. **委托执行**：插件通过 `ctx.Executor` 委托 System/Network/File Executor 执行系统命令
2. **自主执行**：插件自己调用外部 API（如 Docker SDK），但结果仍由 Control Plane 审计

## 7. 设计约束与不变量

### 7.1 安全不变量（不可违反）

| # | 不变量 | 违反后果 |
|---|--------|----------|
| I1 | 用户不可通过 API 传递原始 shell 命令 | 命令注入 |
| I2 | 所有命令通过 Executor 执行，不经 shell | 命令注入 |
| I3 | 所有操作必须经过 Permission Engine 校验 | 越权 |
| I4 | Operation 运行时不可动态注册 | 权限绕过 |
| I5 | 每次执行必留审计记录 | 合规失败 |
| I6 | 插件不可直接执行系统命令 | 审计缺失 + 权限绕过 |
| I7 | 高危操作需要二次确认 | 误操作 |

### 7.2 架构不变量

| # | 不变量 | 说明 |
|---|--------|------|
| A1 | 模块只能向下依赖 | 见 §2.2 依赖规则 |
| A2 | Control Plane 不含业务逻辑 | 见 §1.4 定位约束 |
| A3 | 所有接口接收统一 Context | 见 §4.1 |
| A4 | Capability 由 Engine 统一管理 | 见 P4 |
| A5 | 插件通过 Manifest 声明一切 | 见 §4.6 |
| A6 | 权限 = ResourceType × ActionType | 见 §4.5 |
| A7 | Command 是内核统一操作单元 | 见 P2 |

### 7.3 兼容性约束

| # | 约束 | 说明 |
|---|------|------|
| C1 | DDL 变更必须通过 migration | 不允许直接 ALTER |
| C2 | 新版本可新增字段，不可删除已有字段 | 向下兼容 |
| C3 | API 新增端点可，不改变已有端点语义 | 向下兼容 |

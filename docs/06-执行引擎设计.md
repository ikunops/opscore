# 06-执行引擎设计

> OpsCore Execution Engine Design v1.0  
> 基线文档，冻结后后续 Go 代码按此实现。

---

## 0. 设计目标

解决 OpsCore 最核心的安全矛盾：

```
部署用户：root（后端进程以 root 身份运行）
登录用户：权限不同（SuperAdmin / Operator / Viewer / Auditor）
```

执行引擎是**从"用户请求"到"系统动作"的唯一通道**。只要这条通道设计正确，即使后端进程拥有 root 权限，低权限用户也无法越权执行任何系统操作。

---

## 1. 核心原则

### 原则一：禁止裸命令执行

用户**永远不能**通过 API 传递 shell 命令字符串。

系统只接受 **Operation**（操作）——一个预注册的、参数化的、有权限码的动作。

```
❌ 危险：POST /api/v1/system/exec  body: {"cmd": "systemctl restart nginx"}
✅ 安全：POST /api/v1/system/services/nginx/restart
```

### 原则二：Operation Registry 是唯一命令来源

所有可执行的操作必须预先注册。未注册的操作，执行器直接拒绝。

- 核心操作：引擎启动时注册（system / network）
- 插件操作：插件安装时注册（docker / kubernetes / mysql）

### 原则三：权限码与操作一一对应

每个 Operation 挂载一个 `permission_code`，与 DDL 中 `permissions` 表的 `code` 字段完全一致。

```
Operation: system.service.restart
Permission: system.service.restart（permissions 表中存在此行）
```

用户能否执行此操作 = 用户是否拥有此 permission_code。

### 原则四：命令构建走参数注入，不走 shell 拼接

```go
// ❌ 危险：shell 拼接，存在注入风险
exec.Command("sh", "-c", "systemctl restart "+serviceName)

// ✅ 安全：参数数组，不经过 shell
exec.Command("systemctl", "restart", serviceName)
```

所有命令通过 `exec.Command(name, args...)` 构建，参数经过正则/枚举校验后才注入。

### 原则五：每次执行必留审计

没有不经审计的执行。即使 dry-run 也会记录审计日志（标记 `result=dry_run`）。

## 2. 执行引擎架构

```
┌─────────────────────────────────────────────────────┐
│                    API Layer                         │
│              (HTTP Handler / Router)                 │
└──────────────────────┬──────────────────────────────┘
                       │
                       ▼
┌─────────────────────────────────────────────────────┐
│                 Execution Pipeline                   │
│                                                      │
│  ┌─────────┐  ┌──────────┐  ┌──────────┐           │
│  │  JWT    │→ │  User    │→ │Permission│           │
│  │Middleware│  │ Context  │  │  Engine  │           │
│  └─────────┘  └──────────┘  └────┬─────┘           │
│                                   │                  │
│  ┌──────────┐  ┌──────────┐  ┌───▼──────┐           │
│  │ Policy   │← │Capability│← │ Resource  │          │
│  │ Engine   │  │ Checker  │  │ Checker   │          │
│  └────┬─────┘  └──────────┘  └──────────┘           │
│       │                                              │
│  ┌────▼─────────┐  ┌──────────┐  ┌──────────┐      │
│  │  Operation   │→ │ Dry-Run  │→ │ Executor │      │
│  │  Resolver    │  │  Engine  │  │  (core)  │      │
│  └──────────────┘  └──────────┘  └────┬─────┘      │
│                                        │             │
│  ┌──────────┐  ┌──────────┐  ┌────────▼──┐         │
│  │  Audit   │← │ Result   │← │  Sandbox  │         │
│  │  Writer  │  │ Validator│  │  (exec)   │         │
│  └──────────┘  └──────────┘  └───────────┘         │
└─────────────────────────────────────────────────────┘
                       │
                       ▼
┌─────────────────────────────────────────────────────┐
│              OS Layer (Linux / root)                 │
│         systemctl / iptables / docker / ...          │
└─────────────────────────────────────────────────────┘
```

### 组件职责

| 组件                 | 职责                                 | 失败行为   |
| ------------------ | ---------------------------------- | ------ |
| JWT Middleware     | 解析 Token，提取 user_id                | 401 拒绝 |
| User Context       | 加载用户角色 + 权限列表                      | 401 拒绝 |
| Permission Engine  | 校验用户是否拥有 operation.permission_code | 403 拒绝 |
| Resource Checker   | 校验用户能否访问目标资源                       | 403 拒绝 |
| Capability Checker | 校验目标主机是否具备所需能力                     | 412 拒绝 |
| Policy Engine      | 校验 allow/deny 策略                   | 403 拒绝 |
| Operation Resolver | 查注册表，构建命令，校验参数                     | 400 拒绝 |
| Dry-Run Engine     | 预览将要执行的命令，不实际执行                    | 返回预览   |
| Executor           | 实际执行命令，超时控制，输出捕获                   | 记录错误   |
| Sandbox            | exec.Command 安全封装，资源限制             | 记录错误   |
| Result Validator   | 校验退出码 + 输出特征                       | 标记失败   |
| Audit Writer       | 写入 audit_logs / operation_steps    | 不阻塞响应  |

## 3. Execution Context（执行上下文）

整个链路中传递的上下文对象：

```go
type ExecutionContext struct {
    TraceID    uuid.UUID       // 贯穿审计链路
    RequestID  string          // HTTP 请求 ID

    // 用户信息
    User       UserContext
    // 主机信息
    Host       HostContext
    // 操作信息
    Operation  OperationContext
    // 执行控制
    Meta       ExecutionMeta
}

type UserContext struct {
    ID          int64
    Username    string
    Roles       []string       // ["SuperAdmin", "Operator"]
    Permissions []string       // ["system.service.restart", ...]
}

type HostContext struct {
    ID           int64
    Hostname     string
    Capabilities map[string]json.RawMessage  // {"systemd": true, "root": true}
}

type OperationContext struct {
    Name           string         // "system.service.restart"
    PermissionCode string         // "system.service.restart"
    Params         map[string]any // {"service_name": "nginx"}
    PluginName     string         // 空表示核心操作
}

type ExecutionMeta struct {
    DryRun      bool             // 是否预览模式
    Timeout     time.Duration    // 超时
    Async       bool             // 是否异步
    TaskID      *uuid.UUID       // 异步任务 ID
    ClientIP    string
    UserAgent   string
}
```

## 4. Operation Registry（操作注册表）

### 4.1 Operation 定义

```go
type Operation struct {
    Name           string         // 唯一标识：system.service.restart
    PermissionCode string         // 权限码：system.service.restart
    Description    string
    Category       string         // system | network | plugin
    RiskLevel      RiskLevel      // Low | Medium | High | Critical
    PluginName     string         // 空 = 核心操作；非空 = 插件来源

    // 命令定义
    Command        CommandDef
    Params         ParamSchema

    // 前置要求
    RequiredCapability string     // "systemd" / "docker" / ""
    RequiresHost       bool       // 是否需要目标主机

    // 回滚
    Rollback           *RollbackDef

    // 安全
    Timeout       time.Duration
    MaxOutputSize int            // 字节
    AllowDryRun   bool
}

type RiskLevel string
const (
    RiskLow      RiskLevel = "low"
    RiskMedium   RiskLevel = "medium"
    RiskHigh     RiskLevel = "high"
    RiskCritical RiskLevel = "critical"
)

type CommandDef struct {
    Executable string         // "systemctl"
    Args       []ArgTemplate  // [{"literal": "restart"}, {"param": "service_name"}]
}

type ArgTemplate struct {
    Literal string // 固定字面量
    Param   string // 引用参数名
}

type ParamSchema struct {
    Fields map[string]ParamField
}

type ParamField struct {
    Type     string   // string | int | enum | bool
    Required bool
    Pattern  string   // 正则（string 类型）
    Min      *int     // int 类型最小值
    Max      *int     // int 类型最大值
    Values   []string // enum 类型可选值
}

type RollbackDef struct {
    Operation   string         // 回滚操作名
    ParamMapper string         // 参数映射策略名
    AutoTrigger bool           // 失败时自动触发
}
```

### 4.2 核心操作注册示例

```go
// ===== 系统服务管理 =====

Registry.Register(Operation{
    Name:           "system.service.restart",
    PermissionCode: "system.service.restart",
    Description:    "重启 systemd 服务",
    Category:       "system",
    RiskLevel:      RiskMedium,
    Command: CommandDef{
        Executable: "systemctl",
        Args: []ArgTemplate{
            {Literal: "restart"},
            {Param: "service_name"},
        },
    },
    Params: ParamSchema{Fields: map[string]ParamField{
        "service_name": {
            Type: "string", Required: true,
            Pattern: "^[a-zA-Z0-9_-]+$",  // 只允许字母数字下划线连字符
        },
    }},
    RequiredCapability: "systemd",
    RequiresHost:       true,
    Rollback: nil,  // restart 不需要回滚
    Timeout:       30 * time.Second,
    MaxOutputSize: 1 << 20,  // 1MB
    AllowDryRun:   true,
})

Registry.Register(Operation{
    Name:           "system.service.stop",
    PermissionCode: "system.service.stop",
    Description:    "停止 systemd 服务",
    Category:       "system",
    RiskLevel:      RiskMedium,
    Command: CommandDef{
        Executable: "systemctl",
        Args: []ArgTemplate{
            {Literal: "stop"},
            {Param: "service_name"},
        },
    },
    Params: ParamSchema{Fields: map[string]ParamField{
        "service_name": {Type: "string", Required: true, Pattern: "^[a-zA-Z0-9_-]+$"},
    }},
    RequiredCapability: "systemd",
    RequiresHost:       true,
    Rollback: &RollbackDef{
        Operation:   "system.service.start",
        ParamMapper: "identity",  // 参数直接透传
        AutoTrigger: true,
    },
    Timeout: 30 * time.Second,
})

// ===== 防火墙管理 =====

Registry.Register(Operation{
    Name:           "network.firewall.rule.add",
    PermissionCode: "network.firewall.rule.create",
    Description:    "添加防火墙入站规则",
    Category:       "network",
    RiskLevel:      RiskHigh,
    Command: CommandDef{
        Executable: "iptables",
        Args: []ArgTemplate{
            {Literal: "-A"}, {Literal: "INPUT"},
            {Literal: "-p"}, {Param: "protocol"},
            {Literal: "--dport"}, {Param: "port"},
            {Literal: "-j"}, {Literal: "ACCEPT"},
        },
    },
    Params: ParamSchema{Fields: map[string]ParamField{
        "protocol": {Type: "enum", Required: true, Values: []string{"tcp", "udp"}},
        "port":     {Type: "int", Required: true, Min: ptrInt(1), Max: ptrInt(65535)},
    }},
    RequiredCapability: "iptables",
    RequiresHost:       true,
    Rollback: &RollbackDef{
        Operation:   "network.firewall.rule.delete",
        ParamMapper: "identity",
        AutoTrigger: true,
    },
    Timeout: 10 * time.Second,
    AllowDryRun: true,
})

// ===== 高危操作 =====

Registry.Register(Operation{
    Name:           "system.shutdown",
    PermissionCode: "system.shutdown",
    Description:    "关闭主机",
    Category:       "system",
    RiskLevel:      RiskCritical,
    Command: CommandDef{
        Executable: "shutdown",
        Args: []ArgTemplate{
            {Param: "delay"},  // "+5" = 5分钟后
        },
    },
    Params: ParamSchema{Fields: map[string]ParamField{
        "delay": {Type: "string", Required: false, Pattern: "^\\+[0-9]+$|^now$"},
    }},
    RequiredCapability: "root",
    RequiresHost:       true,
    Rollback:           nil,  // 不可回滚
    Timeout:            10 * time.Second,
    AllowDryRun:        true,
})
```

### 4.3 插件操作注册

插件安装时，通过 Plugin SDK 注册自己的操作：

```go
// docker 插件注册示例
func (p *DockerPlugin) OnInstall(registry *Registry) error {
    registry.Register(Operation{
        Name:           "docker.container.restart",
        PermissionCode: "docker.container.restart",
        Description:    "重启 Docker 容器",
        Category:       "plugin",
        RiskLevel:      RiskMedium,
        PluginName:     "docker",
        Command: CommandDef{
            Executable: "docker",
            Args: []ArgTemplate{
                {Literal: "restart"},
                {Param: "container_name"},
            },
        },
        Params: ParamSchema{Fields: map[string]ParamField{
            "container_name": {Type: "string", Required: true, Pattern: "^[a-zA-Z0-9_-]+$"},
        }},
        RequiredCapability: "docker",
        RequiresHost:       true,
        Timeout:            60 * time.Second,
    })
    return nil
}
```

插件注册操作时，引擎同时向 `permissions` 表插入对应权限码（domain=插件名），并向 `plugin_capabilities` 表写入能力声明。

## 5. Root 权限隔离模型

### 5.1 三层防护

```
┌────────────────────────────────────────────┐
│  Layer 1: 应用层 RBAC（主控制）             │
│                                              │
│  后端进程以 root 运行                        │
│  但每个 Operation 都必须经过 Permission     │
│  Engine 校验，无对应权限码 = 拒绝执行        │
│                                              │
│  Viewer 用户权限列表为空 → 无法触发任何操作  │
└──────────────────┬─────────────────────────┘
                   │
┌──────────────────▼─────────────────────────┐
│  Layer 2: 操作级授权（增强控制）             │
│                                              │
│  高危操作（RiskCritical）需要：              │
│  - 二次确认（double-confirm API）            │
│  - 实时告警通知                              │
│  - 未来可接入审批流                          │
│                                              │
│  例：system.shutdown / firewall.flush       │
└──────────────────┬─────────────────────────┘
                   │
┌──────────────────▼─────────────────────────┐
│  Layer 3: 命令沙箱（纵深防御）               │
│                                              │
│  - exec.Command(name, args...) 不经 shell   │
│  - 超时强制 kill                             │
│  - 输出大小限制                              │
│  - 环境变量白名单（只传安全变量）            │
│  - 子进程资源限制（CPU/内存）                │
└────────────────────────────────────────────┘
```

### 5.2 权限到操作的映射链

```
用户登录
  ↓
JWT → user_id
  ↓
查询 user_roles → roles
  ↓
查询 role_permissions → permissions[]
  ↓
permissions[] = ["system.service.restart", "system.service.read", ...]
  ↓
用户请求 POST /api/v1/system/services/nginx/restart
  ↓
Operation Resolver 查到 operation.permission_code = "system.service.restart"
  ↓
Permission Engine 检查 "system.service.restart" 是否在 permissions[] 中
  ↓
├── 在 → 继续
└── 不在 → 403 Forbidden + audit_logs(result=denied)
```

### 5.3 为什么应用层 RBAC 足够安全

有人会问：后端进程是 root，万一 RBAC 有 bug 怎么办？

回答：

1. **入口收敛**：所有系统操作必须经过 Executor，Executor 只接受已注册的 Operation。没有"执行任意命令"的入口。
2. **参数不可注入**：命令通过 `exec.Command` 参数数组构建，不经 shell。即使参数校验有漏洞，也无法注入管道/重定向/分号。
3. **Operation 不可动态创建**：Operation 只能在引擎启动或插件安装时注册，运行时不可新增。API 无法动态注册操作。
4. **审计不可绕过**：Audit Writer 在 Executor 之后同步执行，即使返回给用户失败，审计也已记录。
5. **纵深防御**：三层防护中任何一层被绕过，其他层仍然有效。

### 5.4 高危操作二次确认

```go
// 高危操作需要两步调用：
// Step 1: 预检 → 返回 confirm_token
// Step 2: 确认 → 用 confirm_token 触发实际执行

// POST /api/v1/system/shutdown
// Request: {"delay": "+5"}
// Response: {
//   "code": 0,
//   "data": {
//     "confirm_token": "abc123",
//     "warning": "即将在5分钟后关闭主机，此操作不可回滚",
//     "expires_in": 60
//   }
// }

// POST /api/v1/system/shutdown/confirm
// Request: {"confirm_token": "abc123"}
// Response: {"code": 0, "data": {"status": "scheduled"}}
```

confirm_token 有效期 60 秒，一次性使用，绑定 user_id + operation + params。

## 6. 安全控制层

### 6.1 预检流程（Pre-Execution Check）

```
Operation 请求到达
    │
    ▼
┌─ Permission Engine ─────────────────────────┐
│  用户权限列表是否包含 operation.permission   │
│  ✗ → 403 + audit(denied)                    │
└──────────────────────────────────────────────┘
    │ ✓
    ▼
┌─ Resource Checker ──────────────────────────┐
│  目标资源是否在用户可访问范围内               │
│  ✗ → 403 + audit(denied)                    │
└──────────────────────────────────────────────┘
    │ ✓
    ▼
┌─ Capability Checker ────────────────────────┐
│  host_capabilities 是否包含 required_capability │
│  ✗ → 412 + audit(denied)                    │
└──────────────────────────────────────────────┘
    │ ✓
    ▼
┌─ Policy Engine ─────────────────────────────┐
│  policies 表中是否有 deny 策略命中            │
│  ✗ → 403 + audit(denied)                    │
└──────────────────────────────────────────────┘
    │ ✓
    ▼
┌─ Operation Resolver ────────────────────────┐
│  1. 查 Registry 获取 Operation 定义          │
│  2. 参数校验（类型/正则/枚举/范围）           │
│  3. 构建命令（exec.Command 参数数组）        │
│  ✗ → 400 (参数错误)                         │
└──────────────────────────────────────────────┘
    │ ✓
    ▼
   进入 Dry-Run 或 Executor
```

### 6.3 命令沙箱（Sandbox）

```go
type SandboxConfig struct {
    Timeout       time.Duration
    MaxOutputSize int
    EnvWhitelist  []string     // 允许传递的环境变量
    MaxCPUPercent int          // 子进程 CPU 限制
    MaxMemoryMB   int          // 子进程内存限制
    WorkingDir    string       // 工作目录
}

func (s *Sandbox) Execute(ctx context.Context, exec string, args []string) (*ExecResult, error) {
    // 1. 不使用 shell
    cmd := exec.CommandContext(ctx, exec, args...)

    // 2. 环境变量白名单
    cmd.Env = s.filterEnv(os.Environ(), s.EnvWhitelist)

    // 3. 输出捕获 + 大小限制
    var stdout, stderr LimitedBuffer
    stdout.MaxSize = s.MaxOutputSize
    stderr.MaxSize = s.MaxOutputSize
    cmd.Stdout = &stdout
    cmd.Stderr = &stderr

    // 4. 启动 + 超时
    if err := cmd.Start(); err != nil {
        return nil, err
    }

    done := make(chan error, 1)
    go func() { done <- cmd.Wait() }()

    select {
    case err := <-done:
        return &ExecResult{
            ExitCode:   cmd.ProcessState.ExitCode(),
            Stdout:     stdout.String(),
            Stderr:     stderr.String(),
            Duration:   cmd.ProcessState.SystemTime(),
        }, err
    case <-time.After(s.Timeout):
        cmd.Process.Kill()  // 强制 kill
        return &ExecResult{
            ExitCode: -1,
            Stderr:   "execution timeout",
            TimedOut: true,
        }, ErrTimeout
    }
}
```

**关键安全点**：

- `exec.CommandContext` 而非 shell 字符串 → 无注入面
- 输出大小限制 → 防止内存耗尽
- 超时 kill → 防止僵尸进程
- 环境变量白名单 → 防止敏感变量泄露给子进程

## 7. 异步任务编排

### 7.1 同步 vs 异步

| 类型   | 判定                     | 示例             |
| ---- | ---------------------- | -------------- |
| 同步执行 | `Timeout <= 30s` 且单步操作 | 重启服务、查状态       |
| 异步任务 | `Timeout > 30s` 或多步操作  | 升级 Docker、批量操作 |

同步操作：API 直接返回结果。  
异步操作：API 立即返回 `task_id`，通过 WebSocket/SSE/轮询获取进度。

### 7.2 任务生命周期

```
                    ┌──────────┐
                    │ pending  │
                    └────┬─────┘
                         │ worker pickup
                         ▼
                    ┌──────────┐
              ┌─────│ running  │─────┐
              │     └──────────┘     │
              │ cancel               │ all steps done
              ▼                      ▼
        ┌──────────┐           ┌──────────┐
        │cancelled │           │ success  │
        └──────────┘           └──────────┘
              │                      │
              │              ┌───────┴───────┐
              │              │ step failed    │
              │              ▼                │
              │        ┌──────────┐          │
              │        │ rolling  │          │
              │        │   back   │          │
              │        └────┬─────┘          │
              │             │                │
              │             ▼                │
              │        ┌──────────┐          │
              └───────→│ failed   │←─────────┘
                       └──────────┘
```

### 7.3 多步骤任务编排

以「升级 Docker」为例：

```json
{
  "task_id": "uuid-xxx",
  "action": "docker.upgrade",
  "steps": [
    {
      "step_no": 1,
      "action": "docker.container.stop",
      "params": {"container_name": "app"},
      "rollback": "docker.container.start"
    },
    {
      "step_no": 2,
      "action": "system.file.backup",
      "params": {"path": "/etc/docker/daemon.json"},
      "rollback": "system.file.restore"
    },
    {
      "step_no": 3,
      "action": "system.package.upgrade",
      "params": {"package": "docker-ce"},
      "rollback": "system.package.downgrade"
    },
    {
      "step_no": 4,
      "action": "docker.container.start",
      "params": {"container_name": "app"},
      "rollback": null
    }
  ]
}
```

### 7.4 回滚机制

```
Step 1 (stop container)  → ✅ success
Step 2 (backup config)   → ✅ success
Step 3 (upgrade package) → ❌ FAILED
    │
    │ 触发自动回滚（逆序）
    ▼
Rollback Step 2 → restore config  → ✅
Rollback Step 1 → start container → ✅
    │
    ▼
Task status = "failed"
Task result = {
    "failed_step": 3,
    "error": "package upgrade failed: dependency conflict",
    "rollback": "completed",
    "rollback_steps": [2, 1]
}
```

回滚规则：

- 从失败步骤的**前一步**开始，逆序执行每个步骤的 `rollback`
- 没有 `rollback` 定义的步骤跳过（标记 `rollback=skipped`）
- 回滚本身失败 → 标记 `rollback=failed`，触发告警
- 回滚过程同样写入 `operation_steps`（`type=rollback`）

### 7.5 Worker Pool

```go
type TaskManager struct {
    queue    chan *Task
    workers  int
    pool     []*Worker
    status   map[uuid.UUID]*TaskStatus  // 内存中的实时状态
}

// 配置
type TaskManagerConfig struct {
    WorkerCount     int           // 默认 4
    QueueSize       int           // 默认 100
    TaskTimeout     time.Duration // 单任务最大超时，默认 30min
    HeartbeatPeriod time.Duration // 状态持久化间隔，默认 5s
}
```

Worker 从队列取任务 → 依次执行 steps → 实时更新 `operation_tasks` 和 `operation_steps` → 通过 WebSocket 推送进度。

## 8. Capability（能力）抽象

### 8.1 两层能力

| 层                   | 来源           | 存储                           | 用途     |
| ------------------- | ------------ | ---------------------------- | ------ |
| HostCapability      | Agent 探测     | `host_capabilities` 表        | 主机能做什么 |
| OperationCapability | Operation 定义 | Operation.RequiredCapability | 操作需要什么 |

执行前检查：`host_capabilities` 是否包含 `operation.required_capability`。

### 8.2 能力探测

```go
// 核心能力探测器（引擎启动时运行）
type CapabilityProbe interface {
    Name() string
    Detect() (json.RawMessage, error)
}

// 注册的探测器
probes := []CapabilityProbe{
    &SystemdProbe{},    // 检测 systemd 是否可用

    &DockerProbe{},     // 检测 Docker 是否安装
    &IptablesProbe{},   // 检测防火墙能力
    &NetworkProbe{},    // 检测网络配置能力

// 探测结果写入 host_capabilities
// {"systemd": true, "root": true, "docker": true, "iptables": true}
```

插件安装时可注册自己的 `CapabilityProbe`，安装后自动探测并写入。

## 9. 审计链路

### 9.1 审计写入点

```
预检拒绝    → audit_logs(result="denied", reason="permission_denied")
Dry-Run     → audit_logs(result="dry_run")
同步执行    → audit_logs(result="success"|"failed", request=..., response=...)
异步任务    → audit_logs(result="task_created") + operation_steps 每步审计
回滚执行    → audit_logs(result="rollback") + operation_steps(type="rollback")
```

### 9.2 审计字段映射

```
audit_logs           ← ExecutionContext
─────────────────────────────────────────
trace_id             ← ctx.TraceID
user_id              ← ctx.User.ID
username             ← ctx.User.Username
permission           ← ctx.Operation.PermissionCode
resource             ← ctx.Host.Hostname
action               ← ctx.Operation.Name
target               ← 操作目标（如服务名/端口号）
request              ← ctx.Operation.Params (JSONB)
response             ← 执行结果 (JSONB)
execute_user         ← 运行用户（root / app）
result               ← success / failed / denied / dry_run / timeout
created_at           ← 执行完成时间
```

### 9.3 审计不可绕过

Audit Writer 是 Executor 的**后置中间件**，不是可选的。即使执行失败，审计也会记录。

```go
func (e *Executor) Execute(ctx *ExecutionContext) (*Result, error) {
    // ... 预检 ...
    // ... 执行 ...
    result := e.sandbox.Execute(...)

    // 无论成功失败，都写审计
    e.auditWriter.Write(ctx, result)  // 同步写入，panic 也写

    return result, nil
}
```

### 核心接口定义

// Executor — 执行引擎入口
type Executor interface {
    Execute(ctx context.Context, req *ExecuteRequest) (*ExecuteResult, error)
    DryRun(ctx context.Context, req *ExecuteRequest) (*DryRunResult, error)
    ExecuteAsync(ctx context.Context, req *TaskRequest) (*Task, error)

type Registry interface {
    Register(op Operation) error
    Get(name string) (Operation, bool)
    List() []Operation
    ListByPlugin(pluginName string) []Operation

// PermissionEngine — 权限引擎
type PermissionEngine interface {
    Check(userPerms []string, requiredCode string) bool
}

// TaskManager — 异步任务管理
type TaskManager interface {
    Submit(task *Task) (uuid.UUID, error)
    GetStatus(taskID uuid.UUID) (*TaskStatus, error)
    Cancel(taskID uuid.UUID) error
    Subscribe(taskID uuid.UUID) (<-chan StepEvent, error)  // WebSocket/SSE
}

## 12. 完整执行链路（冻结）

一次完整的同步操作（以「重启 nginx」为例）：

```
1. 用户 POST /api/v1/system/services/nginx/restart
   Header: Authorization: Bearer <JWT>
   Query:  ?dry_run=false

2. JWT Middleware
   → 解析 Token → user_id=2, username="operator"

3. User Context
   → 查 user_roles → roles=["Operator"]
   → 查 role_permissions → permissions=["system.service.read","system.service.restart"]
   → 构建 ExecutionContext

4. Permission Engine
   → operation.permission_code = "system.service.restart"
   → "system.service.restart" ∈ permissions[]
   → ✅ passed

5. Resource Checker
   → 目标资源 nginx.service 在可访问范围内
   → ✅ passed

6. Capability Checker
   → host_capabilities["systemd"] = true
   → operation.required_capability = "systemd"
   → ✅ passed

7. Policy Engine
   → policies 表无 deny 规则命中
   → ✅ passed

8. Operation Resolver
   → Registry.Get("system.service.restart")
   → 参数校验: service_name="nginx" 匹配 ^[a-zA-Z0-9_-]+$
   → 构建命令: exec.Command("systemctl", "restart", "nginx")
   → ✅ ready

9. Executor + Sandbox
   → 执行: systemctl restart nginx
   → 超时: 30s
   → 输出捕获: stdout="", stderr=""
   → exit_code=0

10. Result Validator
    → exit_code=0 ✅

11. Audit Writer
    → INSERT INTO audit_logs (
        trace_id, user_id=2, username="operator",
        permission="system.service.restart",
        resource="node01", action="system.service.restart",
        target="nginx", request={"service_name":"nginx"},
        response={"exit_code":0,"stdout":""},
        execute_user="root", result="success"
      )

12. Response
    → {"code":0, "message":"success", "data":{"status":"restarted","service":"nginx"}}
```

一次完整的异步多步骤任务（以「升级 Docker」为例）：

```
1. 用户 POST /api/v1/plugins/docker/upgrade
   → 检测到多步骤 → 异步
   → 创建 operation_tasks(status="pending")
   → 返回 {"task_id":"uuid-xxx"}

2. Worker 取任务
   → status="running"
   → WebSocket 推送: {"step":1,"status":"running"}

3. Step 1: docker.container.stop
   → 预检 → 执行 → 成功
   → INSERT operation_steps(step_no=1, status="success")
   → WebSocket 推送: {"step":1,"status":"success"}

4. Step 2: system.file.backup
   → 预检 → 执行 → 成功
   → INSERT operation_steps(step_no=2, status="success")

5. Step 3: system.package.upgrade
   → 预检 → 执行 → 失败 (dependency conflict)
   → INSERT operation_steps(step_no=3, status="failed", output="...")
   → 触发回滚

6. Rollback Step 2: system.file.restore
   → 执行 → 成功
   → INSERT operation_steps(step_no=2, type="rollback", status="success")

7. Rollback Step 1: docker.container.start
   → 执行 → 成功
   → INSERT operation_steps(step_no=1, type="rollback", status="success")

8. 任务完成
   → UPDATE operation_tasks SET status="failed", finished_at=now()
   → audit_logs(result="failed", response={"failed_step":3,"rollback":"completed"})
   → WebSocket 推送: {"status":"failed","reason":"...","rollback":"completed"}
```
